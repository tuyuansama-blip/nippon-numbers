# footy-ev フェーズ2 設計書（較正層 v2 と J1 展開）

**結論**: EPL スパイクの FAIL は**モデルの較正不良ではなく、合格条件そのものの誤設定**である。「市場デシル別 `|model_mean - observed| ≤ 0.05`」は較正（reliability）ではなく**解像度（resolution）を測る指標**であり、`gap_closed ≥ 0.60` という PASS 帯とは数学的に両立しない（§2 で実証）。したがってフェーズ2は「較正層を足して TEST を再実行する」ではなく、**(a) 合格条件を正しい軸に張り直し、(b) 較正層は誤差ドリフト対策の衛生装置として最小構成で入れ、(c) 未見のリーグ群で1回だけ確認する**。

そして本設計の調査で前提がひとつ覆った。**J1 の過去オッズは入手可能である。** `football-data.co.uk/new/JPN.csv` は 2012〜2026 の J1 全 4,543 試合を収録し、うち **4,503 試合に Pinnacle クローズ（PSCH/PSCD/PSCA）が入っている**（§5.1）。「2014年で停止」という前調査の結論は誤り。J1 は EPL とほぼ同一のプロトコルで、n=4,488 のホールドアウトとして一度だけ検証できる。

## 2. 較正条件は誤設定だった（フェーズ2 最大の発見）

### 2.1 実証

**市場デシルで切った表は、モデルが市場より情報量が少なければ、モデルが完全に較正されていても両端が乖離する。** これは較正の欠陥ではなく解像度の定義そのものである。

構成的に**自前スケールで完全較正**な予測器（市場の log 確率にガウス雑音を足し、等調回帰でその場で較正し直したもの）を作り、EPL TEST と同じ n=4,940・同じ市場確率で市場デシル表を引いた結果（各8シード平均）:

| 雑音 sd | gap_closed | 市場デシル最悪 \|gap\| | 自前デシル最悪 \|gap\| |
|---|---|---|---|
| 0.05 | 1.021 | 0.0154 | 0.0110 |
| 0.15 | 0.992 | 0.0222 | 0.0123 |
| 0.20 | 0.966 | 0.0296 | 0.0145 |
| 0.25 | 0.932 | 0.0404 | 0.0189 |
| 0.30 | 0.896 | **0.0529** | 0.0186 |
| **0.35** | **0.856** | **0.0679 ± 0.0065** | 0.0226 |
| 0.40 | 0.813 | 0.0841 | 0.0235 |
| 0.50 | 0.718 | 0.1186 | 0.0263 |

- **実行結果は gap_closed 0.855 / 市場デシル最悪 0.0790。上表の sd=0.35 行（0.856 / 0.0679±0.0065）とほぼ一致する。**両端の値も一致する（実測 top (0.659, 0.738) / bottom (0.134, 0.097)、シミュレーション sd=0.40 で (0.635, 0.722) / (0.142, 0.089)）。
- つまり観測された「平均回帰過多」は、**その解像度の予測器なら較正が完璧でも必ず出る量**である。実測 0.0790 は理論下限 0.0679 の +1.7SD にすぎない。
- 閾値 0.05 を満たすには **gap_closed ≳ 0.90 が必要**。これは STRONG(0.75) より上であり、PASS 帯 [0.60, ...) と重ならない。**DESIGN.md §3 の合格表は自己矛盾していた。**

### 2.2 Murphy 分解による裏づけ（0.1〜0.4）

dc と市場の Brier 差 0.00417 のうち:

```
較正不良（reliability 超過）  0.000259   6.2%
解像度不足（resolution 欠損） 0.00359   86%
残差（分解の丸め）            ~0.0003    8%
```

**モデルに足りないのは情報であって、確率の目盛りではない。**

### 2.3 自前スケールでの較正は合格していた

- dc の不偏 reliability = 0.000244。完全較正な予測器の帰無分布は p99 = 0.000285（0.5）。**帰無仮説の 99 パーセンタイルの内側**。
- dc の自前確率デシル最悪 |gap| = 0.0446。帰無 p99 = 0.0378、閾値 0.05（0.6, 0.7）。**合格**。
- 引き分けチェックは元から合格（+0.0072、許容 ±0.02）。

**DESIGN.md の較正条件のうち、引き分け条件と SE 条件は正しく、市場デシル条件だけが軸を間違えていた。**

## 3. 合格条件 v2（事前登録のやり直し）

### 3.1 差し替える条件

| ID | 条件 | 閾値 | 根拠 |
|---|---|---|---|
| **CAL-1** | 不偏 reliability（3アウトカム プール・等頻度20ビン）| `≤ max(0.02 × Brier_span, 帰無分布の p99)` | 0.02×span は「較正不良が市場との差の2%を超えない」。帰無 p99 は測定分解能の床。EPL では 0.00055 と 0.000285 の大きい方＝0.00055、J1 では床が効いて約 0.00036 |
| **CAL-2** | **自前**確率デシル別 `\|p̄ - ō\|`（n≥150 のビン）| ≤ 0.05 | 完全較正な予測器の帰無 p99 = 0.0378（0.6）。0.05 は帰無をほぼ確実に通し、実質的な歪みは捕まえる |
| **CAL-3** | `\|mean p_draw - 引き分け実測率\|` | ≤ 0.02（据置） | DESIGN.md §3 のまま |
| **CAL-4** | ブートストラップ SE | ≤ 0.003（据置） | 同上 |

- 不偏 reliability の定義: `rel_raw - Σ_b ō_b(1-ō_b)/N`。生の reliability はビン数と n で決まるバイアスに支配される（実測: clim 0.000333 のうち大半がバイアス）ので、**必ず不偏版を使う**。
- 帰無分布は**モデル自身の予測確率から結果を再生成する parametric bootstrap**（200 反復、seed 固定）で run ごとに算出し、レポートに載せる。閾値を人が選ばずに済むのが要点。

### 3.2 降格させる条件

**市場デシル表は診断に降格し、判定には使わない。** ただしレポートからは消さない。代わりに **その run の gap_closed における「完全較正な予測器が示すはずの帯」を §2.1 のシミュレーション手順でその場で計算し、並べて表示する**。乖離が帯の外に出ていれば初めて較正を疑う、という読み方を明文化する。

### 3.3 据え置く条件

`gap_closed_RPS ≥ 0.60`、`gap_closed_LL ≥ 0.55`、CI 上限、FAIL-AUDIT（市場に有意に勝ったらリーク疑い）はすべてそのまま。**FAIL の原因だった条件だけを直し、通っていた条件は一切緩めない。**

### 3.4 新設する報告項目（判定には使わない）

- **Murphy 分解**を model / market / clim について必ず出す。そして `model - market` の Brier 差を「較正不良ぶん」「解像度不足ぶん」に割る（0.4 の形式）。
- これがフェーズ3の投資判断の唯一の根拠になる。解像度不足が 8 割を占める限り、較正・平滑化・正則化の微調整に時間を使ってはいけない。

## 4. 較正層 v2 の設計

### 4.1 位置づけ

**性能装置ではなく衛生装置。** 実測 0.9 のとおり、誠実なオンライン再較正の効果は RPS で 0.00013（市場との差 0.0057 の 2%）。それでも入れる理由は3つ:

1. **J1 の基準率が年ごとに大きく振れる**（引き分け率 0.222〜0.317、ホーム率 0.384〜0.464 / §5.4）。EPL より基準率ドリフトが大きく、追随する仕組みの価値は EPL より高い。
2. **プロダクトの主張が「較正カーブを公開する」であるため**、公開する曲線が自動で真っ直ぐに保たれる機構そのものが商品価値。
3. J1 では TUNE 期間を持たない（§6.1）。凍結定数を持たずに動く層でなければ運用できない。

### 4.2 機構: オンライン・ウォークフォワード再較正

```
予測時刻 t において
  history_t = {(p_k, y_k) : 試合 k のキックオフ < t}      # 厳格 asof、既存の leak gate を再利用
  φ_t = argmin_φ  [ Σ_k w_k · NLL(g(log p_k; φ), y_k) ]  +  λ‖φ - φ_identity‖²
  出力 q = softmax( g(log p ; φ_t) )
```

- **重要な実装点: NLL は「平均」ではなく「和」を使う。** 平均にすると事前分布の相対強度が n に依存しなくなり、序盤で暴れ、終盤で効きすぎる。和にすれば `λ` が有効事前サンプル数として自然に減衰する。
- `w_k` は時間減衰。TUNE の実測（0.9）では**減衰なし（拡張窓）が最良**だったので、既定は `w_k = 1`。半減期つきは事前登録アブレーションとして残す。
- **φ は凍結しない。凍結するのは φ の形・λ・ウォームアップ閾値・リフィット頻度だけ。** これで J1 にリーグ固有の凍結定数を持ち込まずに済む。

### 4.3 関数形の選定（TUNE 実測 0.9 に基づく）

| 形 | パラメータ数 | TUNE LL（誠実オンライン） | 採否 |
|---|---|---|---|
| identity（層なし） | 0 | 0.98240 | 基準 |
| `T`: 温度のみ | 1 | 0.98207 | 予備 |
| **`Tb`: 温度 + H/D オフセット** | **3** | **0.98202** | **採用（本番）** |
| `W`: 3×3 行列 + バイアス | 11 | 0.98150 | 事前登録アブレーションのみ |

```
Tb:  z = log p ;  g(z; φ) = z / exp(φ₀) + (φ₁, φ₂, 0)
```

- **`W` が最良だが `Tb` を採る。** 差は LL 0.0005（RPS では 0.00005 未満）で、TUNE 内のノイズと同オーダー。一方 J1 は序盤 n が小さく、11 パラメータは過学習と数値不安定のリスクが `W` の微差に見合わない。
- `Tb` を採る積極的理由: **ホーム優位と引き分け率という、リーグ間・年次で実際に動く2軸をちょうど吸収する形**になっている（0.14 と §5.4）。`T` 単独ではそれができない。
- 既定値: `λ = 0.003 × n_eff` 相当（= 和形式で `λ = 0.003`）、ウォームアップ `n ≥ 600` 試合、リフィット頻度 = 月次（週次との差は TUNE で有意でなく、計算量が 4 倍になる）。ウォームアップ未達なら φ = identity。

### 4.4 事前登録する受入規則（Do-No-Harm）

較正層は**改善を証明する必要はないが、悪化させないことは証明する必要がある**。

- **CL-1**: TUNE 期間で `RPS(層あり) - RPS(層なし) ≤ +0.0002`。超えたら層は捨てる。
- **CL-2**: 確認 run で CAL-1 と CAL-2 が「層あり」で通ること。「層なし」でも通ってよい（EPL では実際に通る / 0.7）。
- **CL-3**: `φ` の時系列（`exp(φ₀)`, `φ₁`, `φ₂`）を必ずレポートに描く。identity から系統的に離れ続けるなら、それは較正層の成果ではなく**モデル側のドリフトの警報**として扱う。

## 5. 検証プロトコル v2 — どこで事前登録をやり直すか

### 5.1 前提の整理: 何が汚染されたか

| 事項 | 汚染の有無 | 根拠 |

| 較正層の関数形・λ・頻度 | **未汚染** | TUNE 期間の実測（0.9）のみで決定 |

| J1 2012-2025 | **未見・利用可** | 0.12: n=4,488。ただし市場/気候値の**水準**は本設計で測った（0.15）。分母を知った上で閾値を張る点は DESIGN.md §0 と同じ扱い |

### 5.2 決定: 確認 run は「未見リーグ群 → J1」の順で1回ずつ

```
[1] OOS-LEAGUES run（確認・第一）
    対象: E1, SC0, D1, D2, I1, I2, SP1, SP2, F1, F2, N1, B1, P1, T1, G1 の15ディビジョン
          2012/13 - 2024/25（学習ウォームアップに 2005/06 以降を取得）
    使うもの: frozen_params.json をそのまま（ξ, σ, 窓長）。π はディビジョンごとに
              「そのリーグの 2011/12 以前」から機械的に再推定（選択の余地なし）
    判定: §3 の条件表をそのまま適用。ブロックは (div, week_start)
    目的: (a) 修正した合格条件が実際に到達可能であることの確認
          (b) DC + 較正層がリーグを跨いで転移するかの確認 ＝ J1 への転移の予行

[2] J1 run（確認・最終）
    §6。一度だけ。[1] を通過してから実行する

[3] EPL TEST 再スコア（非確認・参考）
    修正条件で読み直した数値をレポートに載せるが、「既読データ」と明記し、
    合否の根拠にはしない
```

**なぜ [1] を先に置くか。** 実装の欠陥・データ層のバグ・条件の解像不足は、必ず最初の大規模 run で露見する。それを J1 で露見させると、product が依存する唯一のホールドアウトを予行演習で使い潰す。未見リーグ群は捨ててよい試験場であり、かつ n≈60,000 で条件の到達可能性を高精度に確定できる。

**なぜ「TUNE で較正層を設計して EPL TEST を再実行」だけでは不足か。** TEST の較正表（両端の乖離量まで）を既に読んでいる。そこで「直った」と報告しても、直す対象を見てから直した以上、確認にならない。

**なぜ 2025/26 を新ホールドアウトにしないか。** 0.10 の実測により Pinnacle クローズが 2026年1月で消滅しており、有効 n=210。CAL-2 のビン下限 n≥150 を満たすデシルが作れない。単独では条件を解像できない。

### 5.3 事前登録で禁じること（実行前に git tag で固定）

1. `frozen_params.json` の値を変更しない。ξ・σ・π・窓長の再探索は禁止。
2. §3 の閾値を確認 run の後に変更しない。
3. OOS-LEAGUES のディビジョン一覧を実行後に増減しない。15本すべてをプールして1つの判定を出す。ディビジョン別内訳は診断のみ。
4. 較正層の関数形を確認 run 後に変えない（`W` へのアブレーションは並記のみ、判定は `Tb`）。
5. run 前に `git tag phase2-preregistered-<date>` を打ち、`frozen_params.json` + `config.py` + 条件表のハッシュをタグメッセージに書く。

### 5.4 OOS-LEAGUES のデータ層で必要な変更

- **チーム同一性は全リーグ手作業のホワイトリストにしない。** 現行 `teams.py` は未知綴りを hard error にするが、15リーグ×約400クラブは維持不能。非 E0 は `team_id = f"{league_id}:{_key(raw)}"` の自動登録に切り替え、`check` は**近傍重複検出**（正規化後の編集距離 ≤ 2 かつ両方が同一シーズンに出現）と「出現 15 試合未満のチーム」の警告のみを行う。E0 と J1 は従来どおり明示表で管理する。
- **スケジュール整合チェックは非 E0 では緩める。** スコットランドのスプリット、ベルギー・トルコ・ギリシャのプレーオフがあるため「N(N−1) 試合」は成立しない。日付・オッズ・重複・オーバーラウンドのチェックのみ有効にする。
- 出現 15 試合未満のチームが絡む試合は学習・評価の両方から除外（下部リーグ混入の防護）。

### 6.3 非リーグ戦の除去（実測で検証済み）

JPN.csv の J1 行にはチャンピオンシップPO・昇格PO が混入し、**J2 同士の試合まで含まれる**（0.20: 2019 の Tokushima vs Montedio Yamagata、2022 の Kumamoto vs Montedio Yamagata など）。放置すると J2 チームの a,d がリーグ平均のスケールに混ざり、強さの尺度が壊れる。

```python
# シーズンごとに
members = {team : 出場数 >= 25}                      # J1 所属クラブ
keep    = 両チームが members に含まれる試合
keep    = keep.sort_values("date").drop_duplicates(["home","away"], keep="first")
```

**この2行で 2012-2025 の全シーズンが正確に `N(N-1)` 試合・各チーム `2(N-1)` 試合になることを実測で確認済み**（306×10季, 380×4季）。進行中シーズンは出場数閾値が使えないので、`members` はシーズン開始時に確定した所属クラブ表（20クラブ）を `config` に持たせて上書きする。

### 6.4 シーズン境界（`season_of` の J1 版）

```python
def season_of_j1(ts):
    # 2012-2025: 春秋制。2月〜12月が同一暦年のシーズン
    # 2026-   : 秋春制。8月開幕・翌5月終幕
    if ts < Timestamp("2026-07-01"):
        return ts.year
    return ts.year if ts.month >= 7 else ts.year - 1
```

| season | ラベル | チーム数 | 期間 |
|---|---|---|---|
| 2012-2020 | `2012`…`2020` | 18 | 2月/3月 - 12月 |
| 2021 | `2021` | **20**（COVID 特例、降格なし） | 2月 - 12月 |
| 2022-2023 | `2022`,`2023` | 18 | 2月 - 12月 |
| 2024-2025 | `2024`,`2025` | **20**（恒久化） | 2月 - 12月 |
| （2026年2-6月） | — | — | **明治安田Jリーグ百年構想リーグ（移行期特別大会・東西2グループ）。JPN.csv に収録なし。既定で学習・評価の両方から除外** |
| 2026- | `2026-27` | 20 | 8月 - 翌5月、12月中旬-2月中旬は中断 |

**`Season` 列を絶対に信用しない。日付から導出する。** 実測で 2026-08-07〜09 の行は `2026/2027`、2026-08-14〜15 の行は `2026` とラベルされており、同一シーズンが2つの値に割れている。`League` 列にも先頭空白の異体（`' J1 League'`）があるので必ず strip する。

### 6.5 昇降格・チーム数変動の扱い

- **モデル側は何も変えない。** DC はチーム索引で持ち、窓はシーズン数で切るので 18→20 も 20→18 も自動で吸収される。変わるのは `check` の期待値と気候値の分母だけ。
- 降格済みチームの過去試合は**尤度に残す**（DESIGN.md §2.2 と同じ。強さのスケールを繋ぐアンカー）。予測対象は当該シーズンの J1 所属チームのみ。
- 入替枠は年で違う（〜2008 入替戦 / 2009-2012 自動3枠 / 2013-2017 PO / 2018-2022 参入PO / 2023 1枠 / 2024- 自動3枠）が、**モデルに入るのは「そのチームが今季 J1 1年目か」だけ**なので、枠数の履歴を実装する必要はない。

### 6.6 昇格チーム事前分布 π の J1 版 — オンライン推定

EPL の π は TUNE 期間で凍結したが、**J1 には TUNE 期間が無い（PSC が初年度から存在するため、構造的にオッズを覗けない期間を切り出せない）。** 凍結値を全期間から推定すればリークする。

```
fold t において
  π_t = ( mean a_i , mean d_i )
        i ∈ {シーズン終了時点の推定値が t より前に確定している「J1 1年目」チーム}
  観測が 3 チーム未満なら π_t = (0, 0)
```

- ウォークフォワードで前向きに更新するだけなので、EPL の凍結 π と**同じ精度で、リークがない**。
- 事前登録アブレーション: `π_online` vs `π=(0,0)` を、**昇格チームが絡む試合のみ**に絞った RPS で比較（DESIGN.md §1.4 と同形式）。差が出なければ π は捨てる。
- **注意（公開すべき既知の弱点）**: 2026-27 昇格組（水戸・長崎・千葉）は 2025年 J2 の成績で昇格が決まっており、我々は J2 の試合を一切見ていない。さらに 2025年12月 → 2026年8月 の 8ヶ月間に「百年構想リーグ」があり、そのデータも無い。**2026-27 の開幕数節は本プロジェクト全体で最も弱い予測**である。事前に宣言し、事後に検証する。

### 6.7 `footy check` の J1 項目

- シーズンあたり `N(N-1)` 行、各チーム `2(N-1)` 試合、`N ∈ {18, 20}`
- `Res` と `HG/AG` の整合、負値・欠損
- `1/PSCH + 1/PSCD + 1/PSCA ∈ [1.00, 1.10]`（実測平均 1.0294 / p99 1.0440）
- `1/BFECH + 1/BFECD + 1/BFECA ∈ [0.98, 1.05]`（取引所なので 1 を下回りうる。実測平均 1.0095）
- `(date, home, away)` の重複ゼロ
- `Season` 列と日付導出シーズンの不一致件数を**警告として出す**（0 にはならない。0 になったら上流仕様が変わった合図）
- チーム名の未知綴り 0 件（J1 は明示表で管理）
- ベンチマーク世代（PSC / BFEC）の切替日を1点だけに保つ

## 7. J1 の検証プロトコル

### 7.1 期間分割（一度決めたら動かさない）

| 期間 | シーズン | n（PSC あり） | 用途 |
|---|---|---|---|
| WARMUP | 2012, 2013 | 606 | 学習データとしてのみ |
| **TEST** | **2014 - 2025（12季）** | **約 3,880** | 一度だけ回す |
| FORWARD | 2026-27 - | 逐次 | 前向き記録。バックテストと**絶対にプールしない** |

- **TUNE 期間を作らない。** 作れば J1 のハイパラを探索することになり、EPL 由来の凍結値という「触っていない」という最大の強みを失う。`frozen_params.json` をそのまま持ち込み、π だけオンライン推定（§6.6）する。これが J1 で最も誠実な構成。
- 2012-2013 を WARMUP に回すのは、6季窓と半減期 365 日のもとで最初のフォールドが極端に薄くなるのを避けるため。

### 7.2 事前登録する分母（実測値・0.15, 0.16）

```
market (Pinnacle close, Shin)     RPS 0.2173   LL 1.0327
climatology (walk-forward)        RPS 0.2338
span = clim - market              RPS 0.0165   （EPL: 0.0393）
Brier span（アウトカム平均）        0.01135     （EPL: 0.02746）
Pinnacle overround                1.0294
H / D / A                         0.4102 / 0.2482 / 0.3416
```

**J1 の獲得可能 skill の総量は EPL の 42% しかない。** これが J1 プロトコルのすべてを支配する。

### 7.3 判定は `gap_closed` ではなく絶対ペア差で行う（J1 固有の変更）

span が小さいので `gap_closed` の分母が小さく、同じ推定誤差が gap_closed 上で 2.4 倍に増幅される。実測 SE の外挿では n≈3,880 でペア差 SE ≈ 0.0008、gap_closed 換算で ±0.05、95%CI 半幅 ±0.10。**gap_closed を主判定に使うと閾値 0.60 を CI が跨いでしまう。**

| 判定 | 条件（すべて span = 0.0165 から導出） |
|---|---|
| **STRONG** | `d_RPS ≤ 0.25 × span = 0.0041` |
| **PASS** | `d_RPS ≤ 0.40 × span = 0.0066` かつ 95%CI 上限 `≤ 0.55 × span = 0.0091` かつ `d_LL ≤ 0.45 × LL_span` かつ CAL-1〜CAL-4 |
| **WARN** | `0.40 × span < d_RPS ≤ 0.60 × span` |
| **FAIL** | それ以上、または較正条件違反、またはリークテスト赤 |
| **FAIL-AUDIT** | `mean(RPS_market - RPS_model) > 0.005` かつ 95%CI 下限 > 0 |

`gap_closed` は**見出しとして CI つきで併記する**が、判定は上表で行う。閾値の比率（0.25/0.40/0.55/0.60）は EPL の 0.75/0.60/... と数学的に同一で、単に分母を EPL 固有値から当該リーグの実測 span に置き換えただけである。**J1 の結果を見てから比率を選んだのではない。**

### 7.4 「誠実さ」の担保

- **リーク防止は DESIGN.md §2.3 をそのまま移植。** ただし J1 は `Time` 列が全行にある（0.12）ので、EPL で泣く泣く「同日は一律使わない」にしていた制約を外し、**キックオフ時刻での厳格 asof** が使える。同日の先行試合を学習に入れられるぶん、EPL より条件が良い。`test_leak.py` の未来削除不変テストは時刻粒度で書き直す。
- **前向き記録とバックテストは別集計。** 市場ベンチマークの世代（PSC → BFEC）も、モデルの版も、較正層の状態も違う。1つの表に混ぜない。
- **代替ベンチマークは不要になった。** 過去オッズが存在するので、気候値のみに頼る必要はない。前向き期間についても BFEC が football-data 経由で翌日には入る。

### 7.5 予測の事前タイムスタンプ固定

三層で担保する。上に行くほど強い。

1. **必須・自動**: 予測ファイル（`predictions/j1_<season>_<round>.json`）を公開 git リポジトリに push。commit 時刻は GitHub 側の第三者記録として残る。ファイルには `asof`（UTC）、`model_version`、`params_hash`、`phi`（較正層の状態）、`odds_snapshot_sha256` を必ず含める。
2. **必須・自動**: 同じ round について、予測生成時点の The Odds API スナップショット（§8）を同時にコミットする。「公開時点で市場が何を言っていたか」を後から作れないようにする。
3. **推奨**: 各 round の予測ファイル群の Merkle ルートを **OpenTimestamps** でビットコインにスタンプする。git の履歴は書き換えうるが、これは書き換えられない。月1回のバッチで十分。

「事後に基準を緩めていないこと」も同じ機構で守る: **§3 の条件表と `frozen_params.json` は `phase2-preregistered-<date>` タグの時点のハッシュを、毎回のレポート冒頭に印字する。**

### 7.6 外れの事後分析（プロダクトの中核コンテンツ）

毎節、RPS 寄与の大きい上位3試合について「モデルの確率」「市場の確率」「結果」「モデルが見ていない情報（負傷・退場・過密日程など）」を定型で出す。**これは分析ではなく、解像度不足がどこから来るかの証拠収集であり、フェーズ3 のデータ投資判断の入力になる。**

## 8. 前向きオッズパイプライン

### 8.1 位置づけの変更

**The Odds API は主ベンチマークではない。** 主ベンチマークは football-data の PSC/BFEC クローズ（§6.1）。理由は実測 0.18: The Odds API 経由の Pinnacle は T−27〜51h でオーバーラウンド 1.049〜1.057 であり、真のクローズ 1.0294 より 2 ポイント以上厚い。**キックオフ直前に寄せても「クローズ」にはならない可能性が高い**（The Odds API 側が Pinnacle の公開サイトを遅延つきで取得しているため）。

The Odds API の役割は3つに限定する:

1. **公開時点の市場状態の証拠**（§7.5-2）。これは football-data では代替できない。
2. **即時に得られる副次ベンチマーク**。football-data は1〜2日遅れるので、当日中の速報にはこちらを使う。ただし「pseudo-close」と明示し、PSC/BFEC と同じ表に混ぜない。
3. **保険**。football-data が J1 を再び落とした場合の唯一の市場データ。

### 8.2 スナップショット → matches 結合の設計

```
data/odds_snapshots/j1_h2h_eu_<UTC>.json        # 生ファイル（現行のまま、追記のみ）
        ↓  footy odds ingest
data/odds_quotes.parquet                        # long 形式・冪等・追記のみ
  event_id, snapshot_ts, commence_time, book_key,
  outcome ('H'|'D'|'A'), price, book_last_update,
  home_raw, away_raw, home_id, away_id, staleness_sec
        ↓  footy odds close
data/odds_close.parquet                          # (event_id, book_key) ごとに1行
```

**必ず守る実装規則:**

1. **`outcomes` は `name` 文字列で `home_team` / `away_team` と照合する。配列 index で取ってはならない。** 実測 0.19 で、同一スナップショット内でも away が先頭に来る試合がある。`name == home_team` でも `name == away_team` でもなく `"Draw"` でもない値が出たら**その試合を丸ごと落として警告する**（黙って落とさない）。
2. **チーム名対応は明示表のみ。ファジーマッチ禁止。** The Odds API と football-data で綴りが違う:

   | The Odds API | football-data JPN.csv |
   |---|---|
   | Hiroshima Sanfrecce FC | Sanfrecce Hiroshima |
   | Kyoto Purple Sanga | Kyoto |
   | Urawa Red Diamonds | Urawa Reds |
   | JEF United Chiba | Chiba |
   | Mito HollyHock | Mito |
   | Fagiano Okayama | Okayama |
   | FC Machida Zelvia | Machida |
   | Shimizu S Pulse | Shimizu S-Pulse |
   | Yokohama F Marinos | Yokohama F. Marinos |

   **`Yokohama F. Marinos` と `Yokohama FC` は別クラブであり、いかなる編集距離マッチでも必ず衝突する。** 明示表以外を使ってはならない。未知綴りは hard error。
3. **疑似クローズは「ファイルのタイムスタンプ」ではなく `bookmakers[].last_update` で選ぶ。** 新しいスナップショットの中にも古い見積りが混ざる。`(event_id, book_key)` ごとに `last_update < commence_time` を満たす最大の `last_update` を採る。
4. `staleness_sec = commence_time - last_update` を全行に持ち、**事前登録した上限（6時間）を超えた行は `close_quality='poor'` として head-to-head 比較から除外**し、除外件数をレポート冒頭に出す。
5. 生の JSON は不変・追記のみ。ingest は何度流しても同じ parquet になること（`(event_id, book_key, book_last_update)` で dedup）。

### 8.3 ブック優先順とフォールバック

```
1. pinnacle                                    （実測 10/10 の試合で存在）
2. 事前登録した16ブックの devig 済み確率の中央値   （下記）
3. 欠損                                        （穴埋めしない。除外件数を出す）
```

- 中央値に使うブック（実測でカバー率 10/10）: `coolbet, nordicbet, unibet_fr, betsson, betclic_fr, winamax_fr, winamax_de, pinnacle, marathonbet, onexbet, betonlineag, tipico_de, pmu_fr, leovegas_se, unibet_se, unibet_nl`。カバー率が低い `betfair_ex_eu(9), sport888(6), williamhill(6), betanysports(1)` は中央値から外す。
- **`Max*` を排した DESIGN.md の趣旨と矛盾しない理由**: 排除の理由は「ブック横断の最良値は取引不能な合成価格だから」。中央値は最良値ではなく中心推定であり、確率のベンチマークとして正当。ただし**単一ブックのクローズより弱いことを前提に、常に `benchmark_source` 列で区別して集計する**。
- H/D/A それぞれについてブック横断で中央値を取ると和が 1 にならないので、中央値を取ってから Shin ではなく**単純正規化**で正規化する（各ブックを個別に Shin 除去 → 確率の中央値 → 正規化、の順）。

### 8.4 スナップショット頻度の評価と改善

**現状（1日2回・固定時刻）は疑似クローズには不適。** 実測 0.18 のスナップショットは、金曜 19:00 JST キックオフに対して T−26.6h、土曜戦に対して T−50h。12時間間隔なので、最良でも T−12h の粒度しか保証できない。

**改善案: キックオフ起点スケジューリング（クレジット消費はむしろ減る）**

```
毎日 1 回:  GET /v4/sports/soccer_japan_j_league/events     # 0 クレジット
            → 今後のキックオフ時刻一覧を取得し、
              30分以内に始まる試合を1つの「クラスタ」にまとめる

各クラスタについて:  T-72h, T-24h, T-6h, T-2h, T-25min の5点で
            GET /v4/sports/.../odds?regions=eu&markets=h2h  # 各 1 クレジット
```

- 1回の `/odds` 呼び出しは**その時点の全未来試合を返す**ので、クラスタ単位で1回打てば同時刻の全試合を覆える。
- 実測の節構成（金2試合 / 土7試合が3クラスタ / 日1試合）から、1節あたりクラスタは 4〜5。**5点 × 4.5クラスタ × 4.3節/月 ≈ 97 クレジット/月**。カップ戦・ミッドウィーク節を含めても 150〜200。月 500 枠に対して 2.5倍以上の余裕がある。
- `commenceTimeFrom/To` や `eventIds` を付けてもコストは変わらない（コスト = markets × regions）ので、絞る必要はない。付けるのはレスポンスを小さくする目的のみ。
- **`x-requests-remaining` を毎回ログし、月内残が 100 を切ったら T−72h/T−24h の点を落として T−2h/T−25min を守る**、というデグレード規則を事前に決めておく。
- 履歴エンドポイント（`/v4/historical/...`）は 10倍コストかつ有料プラン前提。**使わない**（過去は football-data で足りる）。

### 8.5 疑似クローズの品質を毎月検証する

- 疑似クローズ（T−25min の Pinnacle）のオーバーラウンド分布をレポートに常設する。
- **1.04 を継続的に上回るなら「クローズ」と名乗らない。** `pinnacle_t25m` という中立な名前で報告し、football-data の BFEC を主ベンチマークとして扱い続ける。
- 疑似クローズと BFEC が両方ある試合で、両者の RPS 差を毎月測る。これが疑似クローズの「値札」になる。

## 9. 週次運用パイプライン

すべて冪等・再実行可能。`bin/footy weekly` 一発で全段を通し、各段は独立にも走る。

| 曜日(JST) | 段 | 内容 | 失敗時 |
|---|---|---|---|
| 月 09:00 | `fetch` | `JPN.csv` を1リクエスト取得 → `build` → `check` | `check` 赤なら以降を全停止し通知 |
| 月 09:10 | `reconcile` | 前節の結果を matches に反映。予測と突合し RPS/LL を確定。`predictions/*.json` に `result` を追記（**新規ファイルは作らず追記のみ**） | 未確定試合はスキップし翌日再試行 |
| 月 09:20 | `calibrate` | 較正層の φ を更新（月初のみ実行。§4.3 で月次リフィット） | φ 更新失敗なら前回 φ を継続使用（identity には戻さない） |
| 月 09:30 | `report --rolling` | 公開用の較正カーブ・累積 d_RPS と CI・Murphy 分解を再生成 | — |
| 火-木 | `odds`（cron） | §8.4 のキックオフ起点スケジュール | 429/5xx は指数バックオフ。3回失敗でその点を諦め、次の点に賭ける |
| 木 12:00 | `predict` | 次節の予測を生成。`asof = now`。`predictions/j1_<season>_<round>.json` を書く | 学習窓の試合数が閾値未満なら**予測を出さない**（publish gate） |
| 木 12:05 | `publish` | 予測 JSON + 同時刻のオッズスナップショットを git commit & push。タグ `j1-<season>-r<round>` | push 失敗ならリトライ。**push 前に公開先へ出さない** |
| 月次 | `stamp` | 当月の予測ファイル群の Merkle ルートを OpenTimestamps へ | 失敗は警告のみ |
| 月次 | `audit` | CAL-1〜CAL-4 の再評価、φ の時系列プロット、疑似クローズ品質（§8.5）、`params_hash` の一致確認 | CAL 違反または hash 不一致で赤通知 |

**publish gate（予測を出さない条件・事前登録）:**
- `footy check` が赤
- 学習窓の J1 試合数 < 300
- 対象節のチームに `team_id` 未解決がある
- `params_hash` が事前登録タグのハッシュと一致しない

**設計上の要点**: 較正層 φ は「予測時に履歴から再フィットされる状態」であって「別途更新される成果物」ではない（§4.2）。したがって `calibrate` 段が落ちても予測は出せるし、`predict` を過去日付で再実行すればその日の φ が再現される。**運用の段と再現性が分離している。**

## 11. 注意点

1. **§2 の結論をレポートに書かないまま条件だけ差し替えてはならない。** 「基準を満たさなかったので基準を変えた」と外形上は区別がつかない。**差し替えの根拠がシミュレーション（TEST の結果 y を一切使わない）であること**を、再現コードごとレポートに載せる。これがプロダクトの主張「統計的に誠実」の実体そのものである。
2. **J1 の span が EPL の 42% しかない（0.15）ことの含意を過小評価しない。** 同じ実装品質でも J1 の gap_closed は EPL より低く出る。EPL で 0.855 だったから J1 でも 0.85 だろう、という外挿は成り立たない。EPL の絶対ペア差 0.0057 をそのまま J1 に当てはめると gap_closed は 0.65 になる。**PASS ぎりぎりである。**§7.3 で判定を絶対差に移したのはこのため。
3. **BFEC（取引所クローズ）は Pinnacle クローズより「強い」ベンチマークである可能性がある**（オーバーラウンド 1.0095 対 1.0294）。2026年以降のベンチマークが強くなると、**モデル側が何も変わっていなくても d_RPS が悪化して見える。**§6.1 の接続較正を必ず先に測り、世代を跨いだ比較は必ず注記する。
4. **未検証の前提**: (a) OOS-LEAGUES 15本の非 E0 データに DESIGN.md §6.1 と同種の日付パース地雷があるかは未確認。最初に `check` を全リーグで通し、日付レンジがシーズンと整合することを確認してから本 run に入ること。(b) The Odds API の `soccer_japan_j_league` が J1 のみを含むかは公式ドキュメント上の明言がなく、キー名からの推定。実測スナップショット 10 試合はすべて J1 だったが、カップ戦や J2 が混ざらないことは継続監視が必要。(c) football-data の JPN.csv が今後も更新され続ける保証はない。PSC が 2026年に消えたのと同じことが結果データにも起きうる。openfootball を予備ソースとして ingest だけ書いておく。
5. **`W`（11パラメータ）が TUNE で最良だったこと（0.9）を、確認 run の後に「やっぱり W にする」と言い換えてはならない。**§5.3-4 で禁じてある。`Tb` を選んだ理由は小 n での頑健性であり、確認 run の結果とは無関係である。
6. **フェーズ3 の投資先は較正ではない。**0.4 が示すとおり、市場との差の 86% は解像度不足。改善の候補は「xG（ライセンス問題の解決が前提）」「出場メンバー・負傷」「日程過密と移動距離（J1 は EPL より移動が長い）」「市場ブレンド（Benter 2段階）」であり、この順で ROI を見積もること。**較正層の関数形をこれ以上いじって得られるものは実測で 0.0002 未満である。**

**不採用:**
